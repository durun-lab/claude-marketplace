# 決めてほしいこと

段階 0 の試作の結果は [spikes/](spikes/) と[進め方](15-roadmap.md#段階-0-で最初に確かめる難所)。

1. インターフェースのバージョンの検査: 決まった（2026-11-06、ユーザー）。`cargo-semver-checks` を CI に入れた。公開しないクレートでも `--baseline-rev` で動く。API クレートは各自のバージョンを持つ（[CI](../ci.md)）
2. NVDEC の 4K の予算: 決まった（2026-11-06、ユーザー）。予算を fps ではなく「4K60 の素材を同時に何本デコードできるか」で表し、8 本以上とする。実測（`d3d12va` 540〜590 fps、`cuvid` 560〜600 fps）は 9 本分にあたる。前の「4K 700 fps 以上」は、NVDEC 本体が届かない数だった [nvdec](spikes/nvdec.md#4k-の-fps)
3. NVENC で作った 4K の HEVC が `d3d12va` でデコードできない件の原因: 1 フレーム目の `send_packet` が `EINVAL` で失敗する。ffmpeg の CLI 単体でも再現し、`cuvid` は通る。FFmpeg の `d3d12va` か NVIDIA のドライバーか未調査 [nvdec](spikes/nvdec.md#詰まった所)
   - 案 1（55%）: フォールバック（`cuvid`）に任せ、原因は調べない。OBS の NVENC の録画が同じ形かだけ段階 1 で確かめる
   - 案 2（45%）: FFmpeg の最新バージョンと別のドライバーで 1 回再現を取り、上流に報告する。直れば既定の経路だけで済む
   - その他（10%）: `d3d12va` をやめて `cuvid` を既定にする。素材の種類が増えてフォールバックが広がるほど、この案が正しくなる
4. 書き出しの予算を CI のゲートに入れる時期: 書き出し（1080p60）は 13.2 fps で、予算の 120 fps は NVENC 前提。libx264 のままではゲートが失敗し続ける
   - 案 1（65%）: NVENC につなぐ段階 4 まで、書き出しは記録だけにしてゲートに入れない。段階 2 のゲートは `playback` と `scrub` に限る
   - 案 2（35%）: libx264 用の暫定の予算を置き、回帰だけ見る。数は決めていない
5. CEF の別プロセスのアプリへの共有ハンドルの渡し方: CEF が渡す NT ハンドルは CEF のプロセスの中だけで有効。未実装・未測定 [cef](spikes/cef.md#インターフェースに要る変更)
   - 案 1（55%）: `DuplicateHandle` でアプリのプロセスへ複製する。実装は小さいが、ホストがアプリの pid を知る必要がある（`HostSpec` か `Prepare` に足す）
   - 案 2（45%）: ホストが自前の D3D12 共有テクスチャ（`CreateSharedHandle`）へコピーして渡す。wgpu 経由では共有フラグ付きのテクスチャを作れないので生の D3D12 で作る
   - その他（15%）: 最初は同じプロセスで取り込む（試作の形）。段階 6 まで先送りする
6. CEF の 1280x720 で p95 が 26 ms に跳ねる件: 1920 幅固定のページを 1280x720 で描いたときに起きた。原因は未調査 [cef](spikes/cef.md#つまずいた所)
   - 案 1（60%）: 段階 4 の `mm-host-cef` で、ページの幅を大きさに合わせて取り直す。固定幅のページが原因なら消える
   - 案 2（40%）: 今、ページを変えて切り分ける
7. モバイル版の形（[モバイル版の「形」](12-mobile.md#形)）: スマホが iPhone か Android かで C の手間が変わる
   - 案 A（70%）: `mm-serve` が配る PWA。ビルドと配布が PC の中で済み、Preact の画面とパネルのモデルを流用できる
   - 案 B（20%）: durun-dashboard の中の画面。入口が 1 つになるが、movie-maker が単独で動かなくなり、ダッシュボードの中で人と Claude の操作を分ける
   - 案 C（15%）: Tauri 2 のモバイル。端末に複製を持てるが、iOS は macOS と Xcode が要り、複製の同期の仕組みが別に要る
8. 出先からのつなぎ方（[モバイル版の「つながり方」](12-mobile.md#つながり方)）
   - 案 A（80%）: `tailscale serve` の HTTPS から人の待ち受けへ。ダッシュボードと同じ道で、tailnet はすでにある
   - 案 B（25%）: durun-dashboard が人の待ち受けへ中継する。`tailscale serve` の設定が 1 つで済む
   - その他（10%）: Tailscale Funnel か Cloudflare Tunnel で公開し、ログインを足す。tailnet に入れない端末から使うときだけ正しくなる
9. モバイルから即時に適用できる操作の範囲（[モバイル版の「権限」](12-mobile.md#権限)）
   - 案 A（65%）: Story の操作と目印だけ即時。ほかはコメントで Claude に頼み、提案を承認する
   - 案 B（25%）: モバイルの操作は全部提案にし、PC かモバイルで改めて決める。誤りに強いが、自分の操作を自分で承認する手間が増える
   - 案 C（10%）: 全部の操作を即時に受ける
10. PC のアプリが閉じているとき
   - 案 A（55%）: durun-dashboard から movie-maker を起動する（ダッシュボードはすでに起動できる）。PC が起きている前提
   - 案 B（35%）: 画面なしの書き手 `mm serve <project>` を足し、人の待ち受けとコマと HLS を受け持つ
   - その他（15%）: Wake-on-LAN で PC を起こす。PC を眠らせる運用なら要る
11. オフラインの範囲（[モバイル版の「画面」](12-mobile.md#画面)）
   - 案 A（60%）: 接続を前提にし、コメントだけ送信待ちの列に置く
   - 案 B（30%）: Story の操作も送信待ちの列に置き、`base_version` の衝突を画面で解く
   - 案 C（10%）: 端末に複製を持つ（7 の案 C が前提）
12. Claude が対応したときの通知
   - 案 A（60%）: durun-dashboard の通知に任せる（スマホでダッシュボードを開いていれば届く）
   - 案 B（40%）: PWA の Web Push を足す（iOS 16.4 から。ホーム画面に置いたときだけ）

# 決まったこと

1. wgpu のサーフェスと WebView2: 並べられたので、別のウィンドウの案と対案 C（全部ネイティブ）は要らない（2026-11-06、試作の結果）。Tauri の構成を保つ。未確認は 150% の DPI などで、[進め方](15-roadmap.md#段階-0-の終わりの条件の判定)に残した [window](spikes/window.md)
2. NVDEC の経路: `d3d12va` を既定にする。開いた直後の数フレームで失敗する素材（NVENC で作った 4K の HEVC など）は `cuvid` に切り替え、最後は CPU 経由（2026-11-06、ユーザー） [nvdec](spikes/nvdec.md#既定の経路の推奨)
3. 色空間の名前 `bt709`: Rec.1886 の表示の式を指す。BT.709 の OETF は別の名前で持つ（2026-11-06、ユーザー） [ocio](spikes/ocio.md#詰まった所)
4. wgpu をインターフェースに出さない形: インターフェースに wgpu の型を出さず、`GpuHelper` トレイトで囲う形を正式にする（2026-11-06、ユーザー）。RFC と `04-nodes.md` と `14-dev-structure.md` の直しは別の担当が進めている
5. Tauri のアプリで subsecond を使うときの Windows のリソースの二重: 開発のときだけ手当てを使い、本番のビルドには入れない（2026-11-07、ユーザー）。`apps/movie-maker` の feature `hotpatch` のときだけ、`build.rs` が `tauri-build` のリソースをマニフェストだけの `.res` に置き換える（`tauri-build` のコピーは要らなくなった）。上流（`tauri-build` の切り替え、`dx` の `write_winres` を止める）へは報告の文案を置くだけにし、起票はしない [subsecond](spikes/subsecond.md#上流への報告の文案)
