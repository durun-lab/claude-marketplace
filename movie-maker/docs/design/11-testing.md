# テスト

テストは層に分け、層ごとに「何を確かめるか、どこに置くか、ツール、フィクスチャ、いつ回すか」を決める。GPU の要る層はバックエンドごとの期待画像と許容差で扱う。性能のテストは[計装](17-instrumentation.md)の予算をゲートにし、超えたら失敗させる。

## ツールの決まり

- 実行は cargo-nextest。テストごとに別のプロセスなので、GPU のコンテキストや環境変数が漏れず、失敗したテストと時間切れを安全に止められる [58]。
- GPU の要るテストは `[test-groups]` の `gpu = { max-threads = 1 }` に入れ、同時に 1 つだけ動かす [58]。NVENC と NVDEC も同じグループ。
- 時間切れは `slow-timeout = { period = "60s", terminate-after = 2 }`。通しの書き出しと耐久は `[[profile.default.overrides]]` で別の値にする [58]。
- `--retries` は使わない。ゆらぐテストは直すか、ゆらぎの元（時刻、乱数、GPU のバックエンド）を固定する。例外は WebView2 の起動だけ（`--retries 1`）。
- JUnit は `junit.path` で CI に出す [58]。
- 性質テストの失敗した入力は proptest の regressions ファイルに残り、次回から先に試される [55]。コミットに入れる。
- カバレッジは `cargo llvm-cov nextest`（`x86_64-pc-windows-msvc` で動く）[65]。数字を目標にはせず、API クレートの契約テストが実装の行をどれだけ通るかを見る。変異テストは `cargo-mutants` [65] を `mm-ops` と `mm-eval` にだけ月 1 で回す。
- 音とデコードとフレームの比較は、数値の許容差をテストの中に書き、フィクスチャの側には書かない。

## 契約テスト

インターフェースごとに `mm-testkit` に置き、実装を作る関数を渡して呼ぶ（`mm_testkit::decode::contract(|| MyDecoder::new())`）。内容はインターフェースの契約の説明と同じ順に並べる。

| インターフェース | 契約 |
|---|---|
| `mm-node-api` | 既定値で描ける。端（t = 0、t = duration、範囲の外）で例外なし。`vector` なら 2 倍で描けて縁が崩れない。キーが安定（同じ入力で同じキー）。`deterministic` なら 2 回描いて同じ。`time_varying` が偽なら t を変えても同じ。`is_identity` が真なら入力と同じ。`region_of_definition` の外を描かない。`migrate` が古いフィクスチャを通す。`prepare` と `render` が時間切れで戻る。例外を投げたらそのレイヤーだけ透明にしてエラーのフラグを立てる |
| `mm-render-api` | 期待画像。プレビューと `mm frame` で同じフレーム。キャッシュのキーが「ノードの種類、バージョン、評価済みのパラメータ、入力のキー、素材のハッシュ、フレームの番号、品質、色の設定、画面上の大きさ」で決まる。プロジェクトのデータの一部を変えたら影響する時刻の範囲だけ描き直す |
| `mm-decode-api` | フレームの番号と PTS。VFR。先頭のずれ。シークの前後で同じフレーム。プールの使い回し。壊れたファイルでエラーを返してクラッシュしない |
| `mm-color-api` | 変換の往復（入力 → 作業 → 出力 → 入力）が許容差に入る。Rec.709 の既知の値（白、18% グレー）。OCIO と LUT の実装で同じ結果（許容差つき） |
| `mm-audio-api` | 決定性。無音の入力は無音。音量 0 dB はパススルー。ラウドネスの EBU の test set |
| `mm-text-api` | 同じ文字列と字で同じ行組み。空文字。長い 1 語の折り返し。合字と絵文字でクラッシュしない |
| `mm-host-api` | 起動、1 フレームの往復、時間切れ、ホストを kill して再起動して続く。共有テクスチャの受け渡しでハンドルが漏れない |
| `mm-cache-api` | 置く → 引ける。大きさの上限で古いものから消える。消しても作り直せる。別の場所にコピーしても `contentHash` でヒットする |
| `mm-ingest-api` | 付属ファイルの JSON Schema。バージョンの移行 |

`mm-testkit` のモックの実装（単色のフレームのデコーダー、無音のミキサー、矩形の文字）も、同じ契約を通す。

| `ui/mobile/e2e/flow.mjs` | 手順。1 登録（端末がクッキーを保存しないと画面が知らせ、同じ名前で登録し直せる。続けて QR の URL で登録）、2 Watch（親のプレイリスト `index.m3u8` から画質ごとのプレイリストと TS の配信の区間。Chromium は hls.js で再生）と描き込みつきのコメント、3 MCP の `comments` と `propose`（`responds_to`）、4 Proposals で前後のフレームと区間の短い動画（`clip.mp4` の 206。Chromium は `Play` で再生）を見て承認し、別の画面に SSE でコメントの `fresh` が届く、5 Story の `Keep` と「Decide on PC」の提案、6 `setOffline` で書いたコメントが送信待ちのキュー（IndexedDB）に入り、戻ると 1 回だけ届く |

WebKit の Windows 版は HLS と H.264 の MP4 を再生できないので、WebKit はプレイリストと配信の区間、短い動画が取れるところまでを確かめる。
配信の区間の大きさは回ごとに少し違う（符号化が決定的でない）。区間のキーは出力でなく入力から作るので、キャッシュのヒットとミスは変わらない。テストは大きさでなく、TS の同期バイトと区間の数を確かめる。
回すのは段階の締めと、`mm-serve` の人の待ち受け、`mm-stream`、`ui/mobile` を変えた PR。

```sh
# PC の側（FFmpeg ありの設定。配信の区間の符号化に要る）
cd movie-maker
export CARGO_TARGET_DIR=E:/dev/mmt/mobile-e2e CARGO_INCREMENTAL=0
export FFMPEG_DIR=D:/dev/ffmpeg-dev/ffmpeg-n9.0-latest-win64-gpl-shared-9.0 LIBCLANG_PATH="C:/Program Files/LLVM/bin"
cargo build -p mm-serve --example mobile_rig --features mm-runtime/ffmpeg
# PWA と通し。LOCALAPPDATA は MM_E2E_WORK の下に差し替わる
cd ui/mobile && pnpm build
PATH="$PATH:$FFMPEG_DIR/bin" PLAYWRIGHT_DIR=/d/dev/pw \
  MM_RIG=$CARGO_TARGET_DIR/debug/examples/mobile_rig.exe MM_E2E_WORK=E:/dev/mmt/mobile-e2e-work \
```

`MM_E2E_TARGETS=iphone` か `android` で片方だけ回す。
通った回の作業のフォルダー（`MM_E2E_WORK` の `rig-*`）は消す。失敗した回はフォルダーと、失敗した手順の画面（`<端末>-failed.png`）を残す。

### 実機での確かめ方

Playwright の端末の設定は WebKit と Chromium の描画を通すだけで、iOS の Safari の HLS の再生、ホーム画面の Web アプリ、指の操作、4G/5G の回線は実機でしか確かめられない。
iPhone の Safari と Android の Chrome で、それぞれ次を行う。

前提: スマホに Tailscale のアプリを入れ、PC と同じアカウントで tailnet に入っている。PC の Claude Code のセッションが movie-maker の MCP につながっている（[HTTP サーバー](05-ops.md#http-サーバー)）。

1. PC で movie-maker を起動してプロジェクトを開き、[設定の手順](12-mobile.md#設定の手順)の 2〜3 で `tailscale serve status` が `:8443` から `http://127.0.0.1:7338` に向いていることを確かめる。スマホは Wi-Fi を切り、モバイルの回線で Tailscale をつなぐ。
2. PC の Devices パネルで「Add device」を押し、QR をスマホのカメラで読んで開き、`Pair` を押す。Watch の画面に替わり、PC の端末の一覧に名前と Tailscale のアカウントが出る。登録の画面に「did not keep the sign-in cookie」と出たら、Safari の設定の「すべての Cookie をブロック」を切り、PC で登録コードを出し直して同じ名前で登録し直す。
3. iPhone だけ: Safari の共有ボタンから「ホーム画面に追加」を押し、ホーム画面のアイコンから開く。登録の画面が出たら（Safari とクッキーが分かれる）、PC で登録コードを出し直し、名前を `iPhone Home` のように Safari の登録と別にして入れる。
4. Watch で再生する（iPhone は Safari のそのままの再生、Android は hls.js）。一時停止して `Comment` を押し、文を書き、`Draw` で字幕を丸で囲み、`Send` を押す。PC の Review にそのコメントが出る。
5. PC の Claude Code のセッションで「モバイルのコメントに対応して」と頼む（スマホの claude.ai/code からでもよい）。Claude が `comments` で読み、`propose` で提案を出す。
6. Proposals で提案を開き、`Before` と `After` を押して見比べ、`Approve` を押す。Watch に戻るとコメントの状態が `fresh` になっている。PC の画面にも変更が入る。
7. Story で素材を開き、単語を 2 つ押して範囲を選び、`Keep` を押す。続けて `Decide on PC` のチェックを入れ、別の範囲を選んで `Keep` を押す。PC の Review に提案が届く。
8. 機内モードにして `Comment` で書き、`Send` を押す。上に `1 queued` が出る。機内モードを切り、Tailscale がつながると送られ、PC に 1 件だけ届く。
9. 横にして映像が全画面になること、押す所が親指で届くこと、ほかのアプリに切り替えて戻ると読み直されることを見る。終わったら PC の Devices で、この確かめ方で登録した端末を全部外す。

気づいたことは、端末、OS とブラウザーのバージョン、手順の番号を添えて PR かコメントに書く。

## GPU の要るテストの扱い

- バックエンドを固定する。CI は D3D12 の WARP（Windows の CPU のラスタライザ。機能レベル 12_1）[62]、Linux は Vulkan の lavapipe（wgpu の CI と同じ）[62]。実機は RTX の D3D12。
- 期待画像はバックエンドごとに持つ。バックエンドが違うと浮動小数の丸めとフィルタの実装が違う。
- 許容差は 2 段。(1) 同じバックエンド: 輝度の SSIM 0.995 以上かつチャンネルごとの最大の差 2/255 以下（`mm_testkit::golden`。段階 2 の期待画像 10 枚の値で置いた）。(2) バックエンドをまたぐ比較（プレビューと `mm frame` の一致を RTX と WARP で）: SSIM 0.98 以上〔推〕。
- NVDEC と NVENC の要るテストは夜間に実機で回す。CI では `ffmpeg` の実装で同じ契約を通す。
- 別のクレートの実行ファイルに頼るテストは、テストの中で cargo を呼ばず、見つからなければ作り方を書いた文言で失敗する。cargo はワークスペースごとのテスト（`--workspace`）では作るが、`-p` で選んだときは依存先の実行ファイルを作らない。`mm-runtime` の `decode_auto` を `-p mm-runtime` で回すときは、同じ `CARGO_TARGET_DIR` と profile で先に `cargo build -p mm-decode-d3d12va --features d3d12va --bin mm-d3d12va-probe` を実行する（`MM_D3D12VA_PROBE` で別の場所を指してもよい）。
- wgpu の `gpu_test!` の型（全部の GPU で回し、バックエンドごとに「失敗を期待する」を管理する）[62] を `mm-testkit` の `gpu_contract!` に取り入れる。
- 実機の夜間はこの PC で回す。録画中と書き出し中は回さない（[計装](17-instrumentation.md)の「使用中」のフラグを見る）。
- GPU のコンテキストを失った後の復帰（device lost）もテストに入れる。WARP では `DXGI_ERROR_DEVICE_REMOVED` を起こせないので、`mm-render-api` のインターフェースで device lost を注入する。

## 性能のテストと回帰のゲート

- 予算は[計装の予算の表](17-instrumentation.md#予算の表)の 1 つ。テストの側に数を書かない。
- 基礎の層（`mm-eval`、`mm-ops`、`mm-ui-layout`）は divan のベンチで、操作の適用と補間の 1 回あたりの時間を測る。
- 通しの層は `mm perf run <シナリオ>`。フィクスチャのプロジェクトで、再生 30 秒、スクラブ 100 回、書き出し 10 秒、起動を回し、`metrics.jsonl` を出す。
- 比較は `mm perf compare <前> <後>`。Perfherder の型 [48]（閾値を超えた点を、その後の点でも確かめてから警告にする）に合わせ、閾値は項目ごと（既定 5%〔推〕。Firefox は 2% を既定にしているが、GPU の数は揺れが大きい）、1 回の数で決めず、5 回の中央値で比べる。超えたら失敗させる。
- 自動の改善の回は、回の前に `mm perf run` を取り、取り込みの前にもう一度取って比べる（[自動の改善](10-review-improve.md#自動の改善)）。回帰なら取り込まない。
- 夜間の数はアプリのデータの置き場所（[計装の置き場所](17-instrumentation.md#置き場所と大きさ)）に貯め、推移を `mm perf history` で出す。Blender の Open Data が共通のシーンで時系列に貯めるのと同じ型 [51]。

## テストの書き方

- 1 テスト 1 主張。名前は「何をしたら何になる」。
- 時刻と乱数と GPU のバックエンドは、テストが決める。操作と保存（段階 1）の時刻は注入で決め、測定の `Instant::now()` は直接使ってよい。
- 期待画像と数値の許容差は、テストの中に理由つきで書く。
- 失敗したテストは、直すか、失敗する理由を `#[ignore = "理由と issue"]` に書く。理由のない `ignore` は CI で失敗させる。
- WebView の画面のテストは、操作の発行と画面の状態の変化だけを見て、見た目は期待画像に任せる。
